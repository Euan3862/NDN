 \section{Internet Protocol}
The Internet Protocol (IP) is a network layer, layer 3, protocol that facilitates communication between end-points. The basic unit of data transferred by IP is a Datagram. A Datagram is a self-contained, independent piece of data that contains enough information to be forwarded from a source to destination without retaining per-packet state, i.e. an IP router 'forgets' about the Datagram as soon as it leaves the interface.\cite{postel_internet_1981}

\subsection{Internet Protocol Addresses}
 IP endpoints use a 32-bit fixed-length address for Internet Protocol Version 4 (IPv4) and a 128-bit fixed-length address for IPv6 respectively. 
Addresses serve a dual purpose: to identify as addressable endpoint and to indicate the endpoints topological location for routing.\cite{postel_internet_1981}. IP addresses have resulted in several challenges that will be explored below.

 \subsubsection{Address Space Exhaustion}
 IP has faced issues with using addresses to identify endpoints as the original IPv4 used 32-bit addresses, which seemed sufficient at the time of IP's creation ($\sim$1981). The lack of address space faced by IPv4 resulted in additional network layer infrastrure. Classless-Inter-Domain-Routing was introduced to avoid rigid network classes that only allowed for coarse allocation of addresses.\cite{fuller_classless_1993} 
CIDR allowed for arbitrary prefix lengths and route aggregation.
This reduced the wastage of IPv4 addresses caused by assigning too large of a prefix and the routing aggregation allowed for reduced global routing table demands. However, there was still a fundamental lack of IPv4 addresses so Network Address Translation (NAT) was introduced\cite{egevang_ip_1994}. NAT allows for the re-use of a specific range of IP addresses\cite{rekhter_address_1996}. For instance, an endpoint may contain a globally routable address while the nodes downstream from this endpoint use addresses from the private NAT range.
However, this NAT solution introduces more Points of Failure (PoF), disrupts direct network transparency, and increases the computational demand onto the middleboxes that must do address translation to correctly forward Datagrams downstream.


It was realised that these solutions (CIDR ,NAT) would still not be suitable to support a future internet. IPv6 was created and provided larger 128-bit addresses. These 128-bit addressses allowed for a move away from NAT for IPv6 addresses where there exists enough addresses for every endpoint to be globally routable and removing the complexities that come with NAT. However, IPv6 is incompatible with IPv4 because of differently structured header formats so additional infrastructure had to be deployed to provide interfaces in which IPv4 and IPv6 could be translated and interoprable. 


The issue of address exhaustion is not necessarily a problem arising from IP's architecture itself but rather from the unanticipated growth of the Internet. This unexpected growth meant that IPv4 had to be supported with additional network infrastructure. The move to IPv6 has created an Internet split between IPv4 and IPv6 and where infrastructure has to be carefully added to simultaneously support both IP versions.

 \subsubsection{Address Semantics}
 IP addresses acting as an identifier and topological locator creates some issues too. Namely, mobility where the identifier-location coupling is not suitable for Transmission Control Protocol (TCP) connections where a node is mobile. A TCP session is defined by a four-tuple of Source IP, Source port, Destination IP, and Destination port.\cite{postel_transmission_1981} When a TCP node then moves topological location it's IP addresses must also change for routing purposes. This breaks the TCP session and another must be initiated if necessary, which increases latency as well as retransmissions if the session partner is forwarding to the previous IP address before it is updated with the new address. This is unsustainable especially for highly mobile nodes such as a drone which may conceivably move several times in rapid sucession. To counter the issue of mobility, additional complexities must be introduced such as introducing overlay routing like Mobile IP \cite{perkins_ip_1996}, or multipath-capable transport protocols such as Multi-Path TCP and QUIC.\cite{wischik_design_nodate}\cite{langley_quic_2017}

\chapter{Methodology}
    --Accidentally wrote context survey as methodology --very very rough draft
 
    
    IP and NDN comparisons conducted by using a real network where the NDN architecture is realised by encapsulating the NDN packets within an IP Datagram can have several affects on the experimental results. Firstly, the in-network caching of NDN cannot be fully deployed at every node in the network but rather only at specific NDN nodes. As such this would not show the 'true' results of an NDN implementation where every node natively NDN. Also, extra overheads which impact results are introduced because NDN packets must first be encapsulated into an IP Datagram and the IP Datagrams must be decapsulated into NDN packets.   


    This project aims to use only simulation for conducting experiments.
    Using simulation via ns-3 allows for a consistent, deterministic model where confounding variables are minimised.  A test-bed means that the implementation specific details can have a non-trivial impact on the experiment results. For instance, a router with an NDN implementation may be running code that is not optimized to the same level as an IP router, whose code has had decades of iterative optimisation. Also, the behaviors of a network that may impact results, such as congestion and varying link bandwidths are avoided. A simulator based approach allows for implementation details to have a minimised effect and the results to be more representative of the architecture themselves.
